# AI-Assisted Coding @ a bank — 2026-08-12

_generated in 5m 12s_

A full day with 25 engineers at a bank, working in **GitHub Copilot CLI** and **VS Code agent mode** on the `petclinic` repo. The arc: get the agent *tooled up* (memory, skills, CLIs) in the morning, then stop coding and start *specifying* in the afternoon — because once the agent writes the code, the only leverage left is the quality of what you asked for.

## Setup, quotas and the tooling landscape

- Don't adopt someone's [32-agent mega-framework](https://ohmyclaudecode.com/) — build your own, stop where you stop seeing benefit, so you know what's running. ⚓ 32 agents is prohibitive
- Every "agentic framework" is just a folder of **markdown files** — other people's opinions, basically. Nothing to be intimidated by.
- Never run the Copilot plugin inside **JetBrains** 🤮 — keep IntelliJ for reading/reviewing and Alt-Tab to **VS Code agent mode** on the same folder. ⚓ IntelliJ is the shittiest combo on the planet
- Hitting your [credit quota](https://github.com/features/copilot/plans) is the *goal*, not a failure — ask for more the same day; never put a personal subscription on company code (legal exposure). ⚓ costs your boss less than two coffees a day
- One person per spike, then share the scripts with the group — parallel duplicate runs are just burnt tokens.
- The standard bug-fix prompt shape — never just "fix it":
  - `fix bug #40` — let the agent find the tracker itself (GitHub or Azure)
  - reproduce it in a real browser via [Playwright CLI](https://playwright.dev/docs/intro) first
  - write a **failing e2e test**, then fix until green
  - hand back a screenshot/video of before vs after

## Choosing the model and the effort dial

- Route the work to a model yourself; **Auto mode is not a strategy**:
  - **Opus** 🙏 — architecture, planning, spec review, gnarly legacy, large-PR review. *Not offered at the client — riot for it; use **GPT Sol** in the meantime.*
  - **Sonnet** — executing an already-approved plan, coding on a budget
  - **GPT Sol** — reviewing Opus's output; they reason differently and catch each other's glitches
  - **Haiku / mini** — summaries, emails, transcripts
  - **Gemini** — never, for code
- Legacy code is dead-man's territory: **Opus with the 1M context, ≥ medium effort**, always. ⚓ places where people have died
- **Reasoning effort is a second dial**: `high` is the sweet spot, `medium` when on a budget, extra-high only for hard architecture — never `low`.
- Opus for day-to-day coding burns a monthly quota in ≈3 days; that's what Sonnet is for.
- Opus reviewing Sonnet's spec work catches real design decisions Sonnet skipped. ⚓ never join-fetch a paginated query

## AGENTS.md — the project's loaded-by-default memory

- `AGENTS.md` in the repo root is the most important file of 2026; bootstrap it with `/init`, which reads the codebase and writes back what it learned ([AGENTS.md](https://github.com/victorrentea/petclinic/blob/main/AGENTS.md)).
- Prove a memory file is really auto-loaded: plant an absurd line in it, clear the chat, ask about it — the answer arrives with no file read. ⚓ "I have a red Ferrari"
- Too much in `AGENTS.md` pushes the agent into the dumb zone. Keep it ≈100–150 lines and relocate the rest:
  - folder-specific knowledge → a nested `AGENTS.md` in that folder (loaded only when touched) ([AGENTS.md](https://github.com/victorrentea/petclinic/blob/main/petclinic-backend/AGENTS.md))
  - cross-cutting knowledge (Java conventions) → a **skill**
  - …or, if you want it *forced* rather than requested, a **custom instructions file** bound to a glob (java.instructions.md)
  - anything the model already knows from training (how to run tests) → delete it
- Never enumerate in `AGENTS.md` what changes in code (REST endpoints) — it drifts; point at an artifact your tests regenerate. ⚓ test rewrites openapi.yml
- Write down even the "obvious" rules — **GIGO**: an agent that reads your legacy crap will imitate it. ⚓ >120-char lines
- ⭐⭐⭐ Every time the AI produces slop, ask *"what did it not know?"* and add exactly that line; then shrink and de-contradict the file at every retro.
- 🤖 Copilot reads `AGENTS.md`, Claude Code reads `CLAUDE.md` — symlink one to the other rather than maintaining two ([agents.md](https://agents.md/) is the cross-vendor spec).

## Skills, instruction files, and how to distribute them

- A **skill** is progressive disclosure: only `name` + `description` are preloaded; the body is injected on activation, nested files only if the body asks.
- A skill folder is one portable unit (same format for Claude/Copilot/Codex) and can carry:
  - [`SKILL.md`](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/create-skills) with YAML **front matter**
  - extra knowledge files referenced from the body
  - vibe-coded shell/python scripts ⚓ Jacoco uncovered-lines parser
  - output templates and examples
- Make the `description` ≈60 words and state the trigger twice — too terse and the agent silently never activates it.
- A skill is a *polite request*; `.github/instructions/*.instructions.md` with a [**glob**](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions) is the harness force-injecting knowledge whenever a matching file is touched (java.instructions.md). ⚓ `**/*.java`
- 🤖 That force-injection is per matching file, every turn — keep instruction files tiny; a skill you can't get to trigger is usually a description problem, not a reason to promote 300 lines into the glob.
- **Better than a skill is a shell script inside the skill** — fast, deterministic, zero tokens.
- What actually sits above your "hi" in a fresh conversation: the folder's `AGENTS.md`, the tool definitions, and skill *descriptions* only — instruction files are injected later, programmatically.
- Distributing to a team, in increasing maturity: same git repo → shared repo → a **[plugin marketplace](https://agent-plugins.org/)** (a git repo bundling skills, sub-agents and MCP servers, auto-pulled on every change).

## MCP is blocked? Give the agent CLIs instead

- ⭐ **Never copy text to or from the coding agent** — connect it to the source and let it fetch, build and test by itself.
- A ban on [MCP](https://modelcontextprotocol.io/) changes almost nothing — every serious tool has a CLI the agent can just run:
  - **Jira CLI** → Jira and Confluence
  - **Playwright CLI** → a real browser (open the intranet, read your timesheets)
  - **[Azure Developer CLI](https://learn.microsoft.com/en-us/azure/developer/azure-developer-cli) (`azd`)** → issues, build logs, pipeline reruns
  - `psql` / `sqlplus` → explain plans and query tuning
- You can wrap an existing MCP server into a CLI. ⚓ DBHub MCP → CLI
- Poor-man's MCP: a shell script plus a skill documenting how to invoke it — same effect, no server.
- Give the agent a dedicated **read-only DB user**, never your own credentials; a cheap model with write rights near prod is how you get fired.
- Where MCP still genuinely wins: **cloud/remote agents**, which run on a VM that has none of your local CLIs.
- MCP tool definitions are Javadoc for agents — name, "use this when…", typed params — because the model knows only what the schema says ([PetClinicMcp.java](https://github.com/victorrentea/petclinic/blob/main/petclinic-backend/src/main/java/victor/training/petclinic/mcp/PetClinicMcp.java)). ⚓ custom PetClinic `create_visit`
- Turn on **autopilot**: a second small model vets each command, because humans provably cannot spot [malicious bash](https://en.wikipedia.org/wiki/Fork_bomb). Only a Docker sandbox / throwaway VM is actually bulletproof.
- `npm i -g <anything>` runs a stranger's post-install script on your machine — route it through the internal proxy and scan it first.

## Reviewing PRs, and subagents as a context firewall

- Review a PR with **your own** agent even if the author already reviewed with theirs — it spends your quota, and a second agent+human pair sees what the first missed.
- Wire the agent to the DevOps CLI so it posts its findings back as PR comments instead of you retyping them.
- Use **subagents as a context firewall**: they read the 200k tokens and report back ≈300 words, so the orchestrator's context stays clean. ⚓ send minions to explore
- A custom sub-agent file (`.claude/agents/*.md` — front matter, model, allowed tools) is a brainwashed child conversation; the parent becomes an orchestrator and you can't talk to the children directly ([reviewer-efficiency.md](https://github.com/victorrentea/petclinic/blob/main/.claude/agents/reviewer-efficiency.md)).
- 🤖 A subagent can't come back to ask you a question mid-flight — give it everything up front, or it will guess and report the guess as fact.
- Letting the agent write hard-won knowledge into your **home folder is selfish** — move durable lessons into the project git or a shared marketplace repo.

## Context economics and the dumb zone

- The LLM is **stateless**: even a one-letter reply resends the whole conversation. Thinking blocks are discarded each turn; **tool calls persist and are ≈95% of your tokens**.
- Past roughly two-thirds of the context window the agent starts lying — *"all tests pass"*, then *"those were pre-existing failures"*. ⚓ the dumb zone
- Three ways out of a full context, best last:
  - `/compact` — you lose whatever the summary forgot
  - write a handover markdown, review it with human eyes, continue in a fresh chat
  - spawn subagents so the orchestrator never fills up
- Never leave a big session idle for an hour — the server-side **prompt cache** dies and your next word reprocesses everything. ⚓ a $20 "hi"
- 🤖 That cache window is minutes, not hours, by default (an extended TTL is opt-in) — so the cost of a coffee break scales with how big your context already is.

## Grilling the requirement before any code

- A two-line ticket is a **declaration of war** — answer it with questions, starting with *why / what problem are we solving*.
- Plan mode buys you 3–4 questions; the **[grilling prompt](https://github.com/mattpocock/skills/tree/main/skills/productivity/grilling)** buys 15–20. Its load-bearing clauses:
  - "interview me relentlessly until we reach a shared understanding"
  - "walk down each branch of the decision tree, one at a time, wait for my answer"
  - "if you can answer it by exploring the code or tools, research it — don't ask me"
  - "for each question, give me your recommended answer"
- Add *"start with the non-technical questions"* so you can run the interview live with the PO in the room.
- An interview beats a linear assumptions/risks doc: later questions only exist **because of** earlier answers.
- Every grid-like feature has one pivotal question that decides 80% of the code — find it, then repackage it for the business. ⚓ paginate in the browser or in SQL
- Refuse vague requirements column by column — "sortable by any column" collapses on contact with the real columns. ⚓ sort by number of pets
- When the agent claims it inspected your data, **demand the sample rows** — otherwise it answered from the DDL. ⚓ "have you looked at the data?"
- Budget ≈7 hard questions before your brain dies; park the rest in markdown, sleep on it, resume with a colleague.
- Close the brainstorm by dumping the Q&A into `qa.md`, then continue from that file in a fresh conversation (qa.md).

## Spec-driven development, and sizing the ceremony

- **[OpenSpec](https://openspec.dev/)** (`npm i -g @fission-ai/openspec`, then `openspec init`) scaffolds a brownfield spec workflow: `proposal.md` (what & why) → `spec.md` delta → `design.md` (how) → `tasks.md`.
- Match the ceremony to the estimated effort — the day's most useful sizing rule:
  - ≤ half a day → no plan mode, no ceremony: autopilot, then check the work
  - 1–2 days → plan mode, let the agent interview you
  - \> 2 days → written spec markdowns; only about 1 task in 5 earns this
  - unfamiliar tech → a **spike**, not a brainstorm ⚓ first Kafka integration
- Warm up in chat *before* entering plan mode — you can't fight a 40-year architect cold. ⚓ Opus vs a post-meeting brain
- Keep the **proposal in business language** and push every technicality down into the design doc — then patch the workflow markdowns so it happens by default (proposal.md). ⚓ the PO walks out of the review
- Verbose specs are the cheap side of the trade: 40 lines of markdown beats scrolling 600 lines of diff.
- **Never review spec markdowns alone** — expect terms beyond the whole room's competence; have the agent build a 100–200 line demo so the review doubles as training. ⚓ Postgres collation index
- If you haven't rewritten your workflow markdowns in six months, you're a *user* of the vendor's default, not a driver of your own.
- Isolate contexts on purpose: architect in one, hand off a markdown, let a cheaper model implement — you pay tokens to buy focus.

## Closing

- ⭐ When AI fails you, it's **your** missing instruction — enrich `AGENTS.md`, the skill, or the sub-agent file.
- Say *"I vibed that"* when you never read it and *"I built that"* when you reviewed it — flip those two and nobody knows what was actually checked.
- Throwaway tooling nobody will ever read is fine to [vibe](https://x.com/karpathy/status/1886192184808149383); production code is not.
- Grow your agentic workflow ≈2h/week and you're there in 1–2 months.

> *"You will never be the smartest in the room, even if you are alone."* 🙁

## 🎯 Main takeaways

- The model is almost never the bottleneck — what you never wrote down is.
- Stop typing code, start specifying it: the only leverage left is the quality of the question you asked.
- Never be the copy-paste between the agent and your systems — wire it to the source and let it fetch, run and verify.
- Context is the scarce resource, not intelligence: a small clean context beats a big expensive one every time.
- Match the ceremony to the effort — most tasks deserve none, and the rare big one deserves a spec you'd defend in a review.
- Never ship what you haven't read: the agent can write the code, it can never own it.
- Your workflow is a folder of markdown files you own — if you haven't rewritten it in six months, you're running someone else's defaults.
