Acceptance tests express behaviour as plain-English given/when/then scenarios (with assertions in the **`then`** step) so they constrain the agent from the *outside* while a [[spec-driven-development|spec]] constrains it from within.

## Squeeze the AI from both sides

The strategy is to squeeze the chaotic agent between (a) the **design decisions** you anticipated and (b) the **acceptance tests** that must go green. The prompt pattern: *"turn the first two scenarios into [Playwright](https://playwright.dev) feature files — don't implement backing code yet — then implement until they're green."* <span style="color:red">That is behaviour-driven development. Business and testers can *read* it — plain English, no JSON, no null — but they rarely *write* it (see below).</span> For API-level or game clients, [Karate](https://github.com/karatelabs/karate) does given/when/then at the REST level.

<span style="color:red">*"Strangle with two hands"*: the markdown spec where you anticipate the dramas, plus feature files written upfront — the tighter you squeeze, the lighter the review [[2026-08-31-ai-software-vendor]]. **ATDD, not micro-level TDD**: acceptance tests are written **before** implementation and cross-validated by QA + PO + Dev [[2026-08-27-ai-it-services]]. Reflex: when firing a complex requirement, **start with a feature-file test that articulates it** — if it stays red, the AI silently skipped the requirement [[2026-04-27-ai-healthcare-software]]. The "executable specs" dream: feature files run as tests, read as documentation, are validated with the business, and are the source of truth for the spec archive; keep the glue code thin [[2026-04-16-ai-safety-critical]]. [[openspec|OpenSpec]] should emit Gherkin feature files rather than markdown acceptance criteria [[2026-08-31-ai-software-vendor]], and a Scenario Outline generated from the spec's criteria can be embedded as a snippet in `spec.md` — half the tester's work, done [[2026-09-14-ai-industrial]].</span>

<span style="color:red">The broader test strategy behind this — black-box tests at the service seam, why unit tests lost their review value, fixtures and parallelism — has its own page: [[black-box-testing]].</span>

## <span style="color:red">BDD's failed dream — and what survives</span>

<span style="color:red">**Business was never going to author feature files.** Devs hoped it would and [it never happened](https://cucumber.io/blog/collaboration/the-worlds-most-misunderstood-collaboration-tool/); requirements still arrive in Word and Slack [[2026-08-31-ai-software-vendor]] [[2026-09-10-testing-ai-bank]]. BDD means the test is written *and confirmed with the BA before the code*; devs write, the business **validates line by line** [[2026-08-10-ai-consultancy]]. Gherkin is just the language, and it **adds complexity and risk** — the glue code can have bugs. A business-readable **testing DSL** reads the same: the glue doesn't disappear, it *becomes* the DSL functions [[2026-09-10-testing-ai-bank]]. For Cucumber-allergic teams or with no PO to sit with: a small, terse DSL over page objects in business language [[2026-08-27-ai-it-services]] [[2026-08-10-ai-consultancy]].</span>

<span style="color:red">What survives: **[data tables](https://cucumber.io/docs/gherkin/reference#data-tables) / Examples** — parametrised tests, the highest-value feature files — for hard corner cases (case sensitivity, Potter vs potter) and complex business rules where the business thinks in examples, not for trivial scenarios [[2026-08-31-ai-software-vendor]] [[2026-06-02-ai-open-workshop]]. Business finds mundane scenarios boring — use Gherkin where branching is heavy [[2026-09-28-ai-gaming-tech]].</span>

<span style="color:red">**Collaborative workflow**: generate ≈50% of the `.feature` from the ticket → call the business for 10 minutes → complete the rest *together* → the PR carries the feature file so the business confirms it's what they meant — killing "that's not what I wanted" at the source [[2026-05-11-ai-software-vendor]]. Some teams render the feature file from git straight into the ticket, so the business sees exactly the tests running on CI [[2026-06-02-ai-open-workshop]] [[2026-09-16-ai-safety-critical]]. Send `spec.md` to QA **a day before** the [[three-amigos]] meeting so they arrive with the holes already found [[2026-09-14-ai-industrial]]. Converting existing JUnit tests to Gherkin lets you read them word by word with the business; cucumber-jvm runs them in CI like any JUnit test [[2026-05-13-ai-it-services]].</span>

## <span style="color:red">Writing good scenarios</span>

- <span style="color:red">**One scenario per behaviour — after `Then`, no more `When`** (four cases crammed into one were split) [[2026-09-30-ai-enterprise]]. `And` inherits the meaning of its block; keep `Then` purely about outcomes [[2026-06-02-ai-open-workshop]].</span>
- <span style="color:red">**One matched field per scenario** — "search 'Java', find Joe JavaBeans" can't tell whether the name or the address matched. Kill `Then the response status is 200` repeated seven times; it matters only when it's *not* 200 [[2026-04-27-ai-healthcare-software]].</span>
- <span style="color:red">**Simplify scenario outlines aggressively**: one row in the DB, one search-term column, one "finds it: yes/no" column — if a business reader needs >10 s per row, you've lost them [[2026-05-06-ai-ecommerce]].</span>
- <span style="color:red">The same Gherkin can target REST (MockMvc/Testcontainers) or the UI (Playwright + the [Page Object pattern](https://playwright.dev/docs/pom)) by swapping glue — don't make one scenario test both layers [[2026-04-27-ai-healthcare-software]] [[2026-06-08-ai-security-tools]].</span>
- <span style="color:red">Scoping trick: *"the app is on localhost:8080, write 3 Gherkin `.feature` tests for the last screen I worked on — see git"* [[2026-08-06-ai-bank]]. Example: petclinic's [visit-date-range.feature](https://github.com/victorrentea/petclinic/blob/main/petclinic-test/src/visit-date-range.feature).</span>
- <span style="color:red">**Load tests are acceptance criteria too**: "p99 search < 200 ms under 300 concurrent users" → the agent writes the [JMeter](https://jmeter.apache.org)/[k6](https://k6.io)/[Gatling](https://gatling.io) test overnight [[2026-07-23-ai-software-product]].</span>
- <span style="color:red">**Ninja-tester thinking**: write the *one* test that kills you — page size 50 ⇒ crash? a name with a leading space in production data? [[2026-08-27-ai-it-services]]. QA adds **bad inputs**: tab, emoji, "forget previous instructions" in a visit description, so it reaches the logs an agent will later read ([[prompt-injection]]) [[2026-09-02-ai-insurer]]. Prove a fix at interval edges (today+7 passes, today+400 fails), and ask "did you also harden the backend?" — one agent fixed date validation only in the frontend [[2026-09-07-ai-bank]].</span>

## Review acceptance tests, not mock tests

The load-bearing insight: **AI cheats on unit tests** — not by deleting assertions, but by **programming the mock to return exactly what its own implementation produces**. Reviewing 700 lines of mock-coupled unit tests against 500 lines of implementation is "the most worthless activity for a human today." So **review the acceptance tests, and review the code** — let the model's TDD-generated unit tests exist, but don't spend your attention on them. This is the testing face of [[multi-model-review]] and the [[hallucination]] cause of sycophancy ("all tests pass!" — the ones it didn't delete). <span style="color:red">BDD-level end-to-end/API tests give the best safety per review minute ([human-review demo](https://victorrentea.github.io/human-review/demo2/review.html)) [[2026-10-09-ai-jax-london]] [[2026-09-04-ai-software-company]].</span>

**Business-reviewed `.feature` files are the real safety net** — not unreviewed coverage numbers. The collapse story: a team hits 85%+ coverage but never reviews the tests while the AI rewrites them alongside the code, so the net is fake (see [[cognitive-debt]]). Plain-English Gherkin `.feature` files the *business* can read are the layer that actually catches wrong behaviour. A practical `AGENTS.md` rule makes AI-TDD honest: *"after writing tests, summarise in plain English what each test asserts and wait for human approval before implementing"* — a human reviews the **test contracts** (signatures + asserts), not necessarily every value.

<span style="color:red">**Read the glue, read the data.** Gherkin's weak spot is the step code: a feature file "tested" sorting but inserted rows that were already alphabetical — it would pass with no sorting at all; another inserted "ACB" and asserted "ABC" [[2026-07-20-ai-telecom]] [[2026-07-30-ai-safety-critical]] [[2026-08-10-ai-consultancy]]. For UI tests, check the **Playwright trace**, not the code [[2026-09-30-ai-enterprise]]. Even a semantic requirement→test mapping can be satisfied by an `assertTrue` — still open the test code [[2026-09-14-ai-industrial]]. **Don't trust a test you haven't seen fail**: delete the feature from production code and check it goes red ([[mutation-testing]], [[red-green-tdd]]) [[2026-08-27-ai-it-services]] [[2026-05-13-ai-it-services]].</span>

<span style="color:red">**Semantic coverage**: map every test running through the changed code to the spec sentence it covers, and let AI flag **uncovered spec sentences** — requirement-level coverage instead of line coverage ([live demo](https://victorrentea.github.io/human-review/demo/review.html)) [[2026-09-07-ai-bank]] [[2026-09-24-ai-bank]] [[2026-09-28-ai-gaming-tech]]. Ideas on the same line: a plugin colouring `spec.md` green where a test covers it, and replaying real production traffic ([goreplay](https://github.com/buger/goreplay)) to find lines executed in prod but covered by no test [[2026-08-31-ai-software-vendor]]. See [[semantic-coverage]].</span>

## Independence: tests the agent can't see

The independence constraint is critical: QA (or a human) must lock the `.feature` files *before* implementation starts. If the agent generates both the Gherkin and the implementation in the same session, the acceptance tests confirm only what the agent already decided to build — they are not an independent oracle. <span style="color:red">Keep fixtures and `.feature` files **read-only during implementation** [[2026-05-18-secure-coding-payments]] [[2026-07-09-ai-live-casino]]; or run **two parallel agents kept secret from each other** — one writes the glue code, the other the implementation — so tests aren't contaminated by the code [[2026-08-31-ai-software-vendor]]. While one agent implements, a *separate* agent translates the spec into a `.feature` file that goes to the business for sign-off before any glue code [[2026-06-02-ai-open-workshop]].</span>

**Agent-inaccessible test repo.** For fully-autonomous coding loops, keep the acceptance tests in a **separate git repo the coding agent cannot see** — so it can't over-fit or delete them. Reviewers then judge black-box outcomes against tests the agent never read. This is the strongest guard for overnight autonomous runs. <span style="color:red">The reason has a name: **overfitting** — otherwise the agent optimises the implementation to the concrete test cases, not to the requirements. Pro level: acceptance tests written by *another human and their agent*, with a different perspective [[2026-08-13-ai-insurer]] [[2026-08-10-ai-consultancy]].</span>

<span style="color:red">Public examples of these **holdout tests** ("olympiad tests") [[2026-07-09-ai-live-casino]] [[2026-09-14-ai-industrial]] [[2026-10-06-gray-factory-devoxx]]: StrongDM's [software factory](https://factory.strongdm.ai/) (Feb 2026) set the rules "code must not be written by humans" and "code must not be reviewed by humans" — *"validation replaces code review"* — validating with scenario tests instead ([Willison's write-up](https://simonwillison.net/2026/Feb/7/software-factory/)); the sessions describe failures coming back opaque ("requirement 23 didn't pass"), "like university: the prof doesn't hand you the hard tests or you'd cheat". One session summarised OpenAI's [harness engineering](https://openai.com/index/harness-engineering) write-up the same way — the coding agent has no access to the acceptance tests and only hears "you failed requirement 43.2" [[2026-09-07-ai-bank]]. See [[gray-factory]].</span>

## Run them isolated

Drive acceptance tests in a sandbox (e.g. backend + DB + frontend in Docker, headless) — "machines with guns there; it leaves my environment." This is the same containment principle as the [[ralph-loop]]'s Docker sandbox. <span style="color:red">Run new scripts **live in Chrome first** (a visual check), then **headless in Docker** for CI [[2026-04-27-ai-healthcare-software]].</span>

## <span style="color:red">Agentified QA</span>

<span style="color:red">*"It is degrading for a human being to have to test manually that what used to work yesterday still works today"* — Venkat Subramaniam, quoted to free testers for exploratory work [[2026-04-07-ai-product-team]] [[2026-07-06-ai-medical-diagnostics]].</span>

- <span style="color:red">**From story to script**: a tracker MCP pulls the story → AI proposes test cases → **a human reviews** → AI generates Playwright/Cypress scripts following AGENTS.md conventions; when the test case changes, the linked script is adapted. "QA stays the final guardian" [[2026-04-27-ai-healthcare-software]].</span>
- <span style="color:red">**Record → Gherkin**: after the agent clicks through a flow in a real browser, *"add this as an automated headless test, expressed as a Gherkin feature file"* [[2026-05-06-ai-ecommerce]]. **Never re-test by hand**: a tester executes a case once while narrating aloud, then gives the agent the recording/transcript, the plan and app access — the agent writes the Playwright test, and the tester reviews it [[2026-09-04-ai-software-company]] [[2026-09-25-ai-bank-migration]] [[2026-09-30-ai-enterprise]]. Reproduce bugs **hands off the mouse, talking while the AI clicks** [[2026-10-09-ai-jax-london]].</span>
- <span style="color:red">**[Playwright test agents](https://playwright.dev/docs/test-agents)**: a **planner** explores the app into a test plan, a **generator** turns it into tests, a **healer** repairs broken locators (e.g. after a library migration); the docs warn generated tests "may include initial errors" [[2026-07-20-ai-telecom]] [[2026-09-04-ai-software-company]]. "Explore the app and write 10 e2e feature files" took ≈1–2 h for a smoke suite with no hand-written test, and works over untested legacy too [[2026-07-09-ai-live-casino]]. Copying the agents into the project (`npx playwright init-agents`) means they no longer self-update [[2026-09-30-ai-enterprise]]. See [[browser-mcp]].</span>
- <span style="color:red">**Obvious bugs need no human**: tracker CLI pulls the ticket → browser reproduces it → a Gherkin test fails → fix → passes ([demo issue](https://github.com/victorrentea/petclinic/issues/40)); you review the PR "from the park", ideally with a before/after [Playwright video](https://playwright.dev/docs/videos) [[2026-09-25-ai-bank-migration]] [[2026-09-28-ai-gaming-tech]] [[2026-10-09-ai-jax-london]]. Full flow on [[feedback-loop]]. Motto: *"never go to lunch without an agent working."*</span>
- <span style="color:red">During a migration, the cheapest tier clicks old and new screens side by side; humans come last [[2026-09-25-ai-bank-migration]] ([[selenium-to-playwright-migration]]).</span>
- <span style="color:red">QA's role: attend [[three-amigos]] at grooming, auto-generate e2e/API tests when the app hits test, and shift manual work to **exploratory testing** (odd combinations, two tabs, curiosity) — a target of ≈5 newly automated tests per tester per week [[2026-07-09-ai-live-casino]] [[2026-09-14-ai-industrial]]. A failing Sonar gate fails the build, so the agent wakes up by itself and cleans until it passes [[2026-08-27-ai-it-services]].</span>
